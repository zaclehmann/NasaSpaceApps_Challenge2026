## Architecture decisions

| Decision | Choice | Why |
| --- | --- | --- |
| API host | **Vercel serverless functions (Node)** in the same project as the web app | Same domain (no CORS), no always-on server to keep awake, free for a hackathon. Free always-on Node hosts tend to sleep, which gives judges a blank screen. |
| Framework | Plain Node handlers in `apps/server/src/handlers`, exposed through `api/*.ts` Vercel functions | Thin, testable, no framework to fight. The handlers are plain functions, so they can run under Fastify later. |
| Database | **Supabase (Postgres)** | Your choice. Story: Supabase is Postgres and can be self-hosted, so on a spacecraft it would run on the onboard server. |
| DB access | Server only, with the **service role key** in Vercel environment variables. Row Level Security on, with no public policies | The browser never talks to Supabase and never sees a key. |
| What's stored | Everything the astronaut does: entered readings, symptoms, routine completions, alert acknowledgements and actions, reports, demo settings | These are the "gathered" data. |
| What's computed | Live shirt readings and habitat radiation are generated by the simulator on the server from seed + time + scenario | No write every 5 seconds, and no gaps if the function is idle. |
| Judges sharing one database | Every row carries a **session id** made in the browser (`localStorage`) | One judge's Acknowledge never changes another judge's screen. |
| Live updates | The browser polls the API every 5 seconds | Serverless can't hold WebSockets; polling matches the 5-second sensor rate. |
| Fallback | If the API fails or times out (3 s), the app switches to the in-browser simulator and shows "Onboard server: offline, local mode" | The app always works, including weeks later during global judging. |

**Risk to note:** free Supabase projects can pause after a period of inactivity, and global judging runs for weeks after the deadline. The fallback keeps the demo working either way. Check the Supabase dashboard occasionally during judging.

## Phase R: real NASA radiation data (1.25 h)

The source is NASA's DONKI (Space Weather Database Of Notifications, Knowledge, Information), run by NASA's Community Coordinated Modeling Center. Its web service needs no key:
`https://kauai.ccmc.gsfc.nasa.gov/DONKI/WS/get/SEP?startDate=2024-05-01&endDate=2024-05-31`

Checked today: May 2024 returns 14 solar energetic particle (SEP) events, including:
- `2024-05-10T13:35Z`, GOES >10 MeV, linked to the X-class flares and CMEs of 8 to 10 May.
- `2024-05-11T02:10Z`, GOES >100 MeV.

This is the May 2024 "Gannon" solar storm, a strong, well-known real event.

**What DONKI gives and doesn't give:** event times, instruments, linked flares and CMEs, and links to NASA pages. It does **not** give a radiation dose. So the timing and sequence are real; the dose rate in the habitat stays simulated and is labelled so.

| Step | Work | Done when |
| --- | --- | --- |
| R1 | Script `scripts/fetch-donki.mjs` downloads SEP, FLR (flares) and CME for 2024-05-08 to 2024-05-14 and writes `packages/shared/data/donki-2024-05.json` (trimmed to the fields used, plus the source URL and fetch date). Run once; commit the JSON. | JSON committed; no network call at runtime |
| R2 | The "Solar particle event" scenario replays the real sequence on the mission clock: flare, then CME, then SEP onset (>10 MeV), then >100 MeV peak, with the real time gaps between them (compressed into the demo window if needed, with the compression factor shown). The simulated dose rate rises at the >10 MeV onset and peaks after the >100 MeV event. | Scenario timing comes from the JSON, not hard-coded numbers |
| R3 | UI: the radiation panel and chart show "Event sequence: NASA DONKI, May 2024 solar storm" with a link, and markers for flare, CME and SEP onset on the radiation chart. The "Why" text says the timing is real and the dose is simulated. | Visible in the panel and chart; link opens the DONKI page |
| R4 | Methodology › Data sources and README › NASA data: name DONKI, the dates, what's real and what's simulated. | Both updated |

Tests: the scenario builder places events in the right order and gaps; the JSON loader rejects a malformed file.

## Phase S: Node API + Supabase (3.5 h)

### S1. Database schema (30 min)

SQL migration in `apps/server/supabase/migrations/001_init.sql`, run in the Supabase SQL editor:

| Table | Key columns |
| --- | --- |
| `sessions` | `id` (uuid, from the browser), `created_at`, `scenario`, `astronaut_id`, `earth_link_up`, `sleep_period`, `mission_setting` |
| `entered_readings` | `id`, `session_id`, `astronaut_id`, `indicator`, `value`, `value2` (diastolic), `context` (glucose timing), `taken_at` |
| `symptoms` | `id`, `session_id`, `astronaut_id`, `body_part`, `symptom`, `severity`, `note`, `logged_at`, `resolved_at` |
| `routine_completions` | `id`, `session_id`, `astronaut_id`, `task_id`, `day`, `completed_at`, `postponed_until` |
| `alert_events` | `id`, `session_id`, `astronaut_id`, `indicator`, `severity`, `opened_at`, `acknowledged_at`, `resolved_at` |
| `alert_actions` | `id`, `alert_event_id`, `kind`, `note`, `at` |
| `reports` | `id`, `session_id`, `astronaut_id`, `urgency`, `note`, `summary_json`, `queued_at`, `sent_at` |

- RLS enabled on all tables; no policies (server uses the service role key).
- Indexes on `(session_id, astronaut_id)`.
- Seed: none needed. History comes from the simulator; a new session starts from the same seeded state as today.

### S2. Server handlers (1 h)

`apps/server/src/`:
- `db.ts`: Supabase client from env vars; fails loudly if they're missing.
- `simulate.ts`: imports the existing seeded simulator from `packages/shared` (move it there from `apps/web/src/data/mockSource.ts` so both sides use the same code) and computes live readings for any time.
- `handlers/*.ts`: one per endpoint, plain functions `(input, ctx) => result`, with input validated by **zod** schemas in `packages/shared` (one new dependency).

Endpoints (all under `/api`, JSON):

| Method | Path | Does |
| --- | --- | --- |
| GET | `/health` | `{ ok, db: "up" or "down", time }` |
| GET | `/state?session&astronaut` | Everything the screen needs: crew, mission, indicators with values and statuses, routine, alerts, symptoms, downlink queue |
| GET | `/readings?session&astronaut&indicator&window` | Chart series |
| POST | `/readings` | Save an entered reading; returns new status |
| POST | `/symptoms` | Log a symptom |
| POST | `/routine/complete`, `/routine/postpone` | Routine actions |
| POST | `/alerts/:id/acknowledge`, `/alerts/:id/actions` | Acknowledge, log an action |
| POST | `/reports` | Queue a report to the flight surgeon |
| POST | `/demo` | Scenario, Earth link, sleep period, mission setting, astronaut; or reset the session |

Status and alert logic: reuse `getStatus` and the alert rules from `packages/shared`. The server decides statuses; the browser only displays them.

### S3. Vercel wiring (30 min)

- `api/[...path].ts` routes to the handlers (one function keeps cold starts down).
- `vercel.json`: build command, `apps/web/dist` as output, SPA fallback for every non-`/api` route.
- Local dev: `vercel dev` runs web + API together.

### S4. Web client (1 h)

- `apps/web/src/data/httpSource.ts` implements the existing `DataSource` interface with `fetch`, polling every 5 seconds.
- `apps/web/src/data/pickSource.ts`: try `GET /api/health` (3 s timeout). If it's OK, use `httpSource`; otherwise use the mock and show the local-mode notice. A `?local=1` link forces the mock (handy for recording the video).
- Header: add "Onboard server: connected" (or "offline, local mode" with a Watch badge) next to the Earth link, as two separate states, as planned from the start.
- Session id: made on first load, kept in `localStorage`; Demo › "Reset demo" makes a new one.

### S5. Tests (30 min)

- Handler tests with a fake database (no network): save reading → status changes; acknowledge → alert acknowledged; session isolation (two sessions don't see each other's rows).
- One smoke test against `vercel dev`: health, state, post a reading, read it back.
